## 先看两套协议的"整条链路"

### HTTP 的完整链路（你看网页）

```
你输入网址
    ↓
浏览器拼 HTTP 请求包： "GET / HTTP/1.1 Host: baidu.com"
    ↓
TCP 把这个包切成小片，编号，保证顺序
    ↓
IP 给每片写上源地址和目标地址
    ↓
网卡转成电信号，走网线/WiFi
    ↓
百度服务器收到，原路返回数据
```

**本质：一个进程（浏览器）请求另一个进程（服务器）手里的静态资源。**

---

### MCP 的完整链路（我调 Excel 工具）

```
你对我说"读一下这个 Excel"
    ↓
我（AI）拼 MCP 消息： { "jsonrpc": "2.0", "method": "tools/call", ... }
    ↓
走 HTTP 或 stdio（标准输入输出流）传输
    ↓
MCP 服务器（Excel 工具进程）收到消息
    ↓
Excel 工具去实际读取文件
    ↓
返回结果： { "jsonrpc": "2.0", "result": "表格内容..." }
    ↓
我收到结果，告诉你
```

**本质：一个进程（AI）要求另一个进程（工具）帮它做事情，不只是取数据。**

---

## 底层核心差异对比

### 1. 消息格式（线路上实际传的东西）

**HTTP 报文：**
```
GET /api/weather HTTP/1.1
Host: weather.com
User-Agent: Chrome
                      ← 空行分隔
{"city": "北京"}      ← 请求体
```

**MCP 报文：**
```json
{
  "jsonrpc": "2.0",     ← MCP 基于 JSON-RPC 协议
  "id": 1,              ← 每次请求有唯一 ID，可以配对
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": { "city": "北京" }
  }
}
```

MCP 基于 **JSON-RPC**（远程过程调用协议），这是最关键的底层区别。

---

### 2. 通信模型

| | HTTP | MCP |
|--|------|-----|
| **模型** | 资源导向（REST） | 动作导向（RPC） |
| **核心** | "我要某某资源" | "我要你做某件事" |
| **例子** | `GET /weather` 拿天气数据 | `call tool "get_weather"` 让工具去查天气 |
| **语义** | CRUD（增删改查） | 调用能力（做动作） |

翻译成人话：
- **HTTP 像点外卖**："给我来一份宫保鸡丁"（你给我一个现成的东西）
- **MCP 像请人干活**："帮我把这块木头做成桌子"（你帮我完成一件事）

---

### 3. 传输方式（MCP 独有的灵活性）

MCP 的底层传输有两种：

| 传输方式 | 怎么理解 | 什么场景用 |
|---------|---------|-----------|
| **stdio** | 你启动一个子进程，通过"标准输入/输出"和它对话 | 本地工具，比如读本地文件、操作本地数据库 |
| **HTTP (SSE)** | 通过 HTTP 长连接通信，服务器可以主动推消息 | 远程工具，比如调用云端 API |

**这就是你那个 readme 里写的：**
> 跨本地的进程调用就是 stdio，跨远程的进程调用就是 http

**stdio 底层长这样：**
```
MCP 客户端（AI）                  MCP 服务器（工具进程）
    │                                │
    │  启动子进程（node tool.js）     │
    │ ──────────────────────────→    │
    │                                │
    │  往 stdin 写：调 get_weather    │
    │ ──────────────────────────→    │
    │                                │
    │  从 stdout 读：返回 30°C       │
    │ ←──────────────────────────    │
```

HTTP 做不到 stdio 这种本地进程间通信，这就是 MCP 在本地场景的独特优势。

---

### 4. 有无状态

| | HTTP | MCP |
|--|------|-----|
| **状态** | 无状态，每次请求都是陌生人 | **有会话**，建立连接后保持对话上下文 |
| **意味着** | 每次都要带 token 证明你是谁 | 可以持续对话，工具可以记住中间状态 |

MCP 建立连接时有一个 **initialize** 握手过程，类似 TCP 的三次握手：

```
MCP 客户端                    MCP 服务器
    │                            │
    │  initialize（自我介绍）      │
    │ ────────────────────────→  │
    │                            │
    │  initialized（知道了）       │
    │ ←────────────────────────  │
    │                            │
    │  然后开始反复调工具         │
    │ ────────────────────────→  │
    │ ←────────────────────────  │
```

---

### 5. 协议分层对比

```
┌──────────────────────────────────────┐
│        应用层                         │
│                                      │
│  ┌──────────┐    ┌──────────────────┐│
│  │  HTTP    │    │  MCP (JSON-RPC)  ││
│  │ 客户端↔   │    │  AI ↔ 工具       ││
│  │  服务器   │    │                   ││
│  └────┬─────┘    └────────┬─────────┘│
│       │                   │           │
│  ┌────▼───────────────────▼─────────┐│
│  │  传输层：TCP                      ││
│  │  （保证数据不丢不乱）               ││
│  └────┬────────────────────────────┘│
│       │                              │
│  ┌────▼────────────────────────────┐│
│  │  网络层：IP                      ││
│  │  （路由寻址，送到正确的机器）       ││
│  └─────────────────────────────────┘│
└──────────────────────────────────────┘
```

**关键点：HTTP 和 MCP 都跑在 TCP/IP 之上，是同级的应用层协议。** 但 MCP 也可以不走网络，直接走 stdio（进程内的管道通信）。

---

## 总结成一句话

| 维度 | HTTP | MCP |
|------|------|-----|
| 底层协议 | TCP/IP | TCP/IP **或** stdio（管道） |
| 消息格式 | HTTP 报文（文本协议） | JSON-RPC（结构化 JSON） |
| 通信模型 | 请求-响应，拿资源 | 请求-响应，调用动作 |
| 有无状态 | 无状态 | 有会话 |
| 谁和谁 | 浏览器 ↔ Web 服务器 | AI ↔ 工具（任何语言写的） |
| 典型场景 | 刷网页、调 API | 让 AI 读文件、查天气、操作 Excel |

**HTTP 是"你给我数据"，MCP 是"你帮我去做"——这是最根本的区别。**


## 总结：API 的三层含义
含义 调用方式 例子 网络 API 通过 HTTP 请求 fetch('https://api.baidu.com') 库 API 引入后直接调函数 axios.get() 、 _.filter() 语言/运行时 API 语言自带，直接用 document.getElementById() 、 fs.readFile()

核心本质都是一样的：别人写好的功能，你通过约定好的接口来调用。 区别只是这个"别人"是谁——是远程服务器、第三方库、还是语言本身。
