# 用一个最小 Demo 讲清楚 RAG：LangChain + MemoryVectorStore 入门实战

> 运行未验证。本文基于本地材料做静态分析，适合刚开始接触 RAG、想先看懂“检索增强生成到底是怎么串起来”的开发者。

很多人第一次学 RAG，会被一堆名词绕晕：Embedding、向量库、Retriever、Prompt Augmentation……看完概念还是不知道代码到底怎么流动。这个 `rag-demo` 项目比较适合入门，因为它没有一上来就接复杂数据库，而是用一个很小的 LangChain 示例，把 **文档组织、向量检索、上下文拼接、模型生成** 这条主链路完整走了一遍。

这篇文章我不讲“万能方案”，只讲这个 demo 真正做了什么、为什么这样做，以及它离生产可用还差哪些关键能力。

## 这不是“大模型记住知识库”，而是“先查再答”

RAG 的核心思想其实很朴素：

1. 先准备知识材料
2. 把知识材料变成可检索的向量
3. 用户提问时，先查到相关片段
4. 再把这些片段交给大模型回答

也就是说，大模型不是直接“知道”你的私有知识，而是在回答前临时拿到上下文。

这个项目就完整体现了这件事。

## 项目里到底用了哪些东西

从 `package.json` 能看到，它的依赖非常聚焦：

- `dotenv`
- `@langchain/openai`
- `@langchain/core`
- `@langchain/classic`

对应职责也很清晰：

- `dotenv`：加载环境变量
- `ChatOpenAI`：负责最终生成回答
- `OpenAIEmbeddings`：负责把文本转成向量
- `Document`：定义知识片段
- `MemoryVectorStore`：在内存里完成向量存储和相似度检索

这也是这个 demo 好懂的原因：它只保留了 RAG 最关键的骨架，没有引入太多工程噪音。

## 先看知识库：不是一整篇文章，而是一段段 Document

在 `src/index.mjs` 里，项目直接手写了多个 `Document` 对象，内容围绕“光光”和“东东”的友情故事展开。每个文档都包含两部分：

- `pageContent`：参与 embedding 的正文
- `metadata`：不参与向量化，但可用于分类、过滤和溯源

例如这些元数据里有：

- `chapter`
- `character`
- `type`
- `mood`

这一点特别值得初学者注意：

> 在 RAG 里，真正被“语义检索”的往往不是整个知识库，而是一个个被切好的文档片段。

这个 demo 没有再做额外切分，而是直接把每个故事段落当成一个检索单元。因为材料很短，所以这样写完全够用。

## Embedding 在这里做的事，不是生成答案

很多人第一次接触时，容易把 embedding 和大模型生成混在一起。

这个项目把两者分得很开：

```js
const model = new ChatOpenAI({
  temperature: 0,
  model: process.env.MODEL_NAME,
  configuration: {
    baseURL: process.env.OPENAI_BASE_URL,
  }
})

const embeddings = new OpenAIEmbeddings({
  model: process.env.EMBEDDING_MODEL_NAME,
  configuration: {
    baseURL: process.env.OPENAI_BASE_URL,
  }
})
```

这里其实做了两件完全不同的工作：

- `ChatOpenAI`：负责最后把上下文组织成自然语言回答
- `OpenAIEmbeddings`：负责把“文档”和“问题”都映射到同一个向量空间

只有进入同一个向量空间之后，系统才知道“这个问题和哪几个文档语义更接近”。

## 向量库是怎么建起来的

项目里最关键的一句是：

```js
const vectorStore = await MemoryVectorStore.fromDocuments(documents, embeddings)
```

它背后相当于完成了两个步骤：

1. 把 `documents` 中所有 `pageContent` 做 embedding
2. 把得到的向量放进 `MemoryVectorStore`

这里用的是 **内存向量库**，不是 PostgreSQL、Milvus、Pinecone 这类外部存储。

这意味着它的优点很明显：

- 上手简单
- 零额外部署成本
- 很适合教学和原型验证

但边界也同样明确：

- 程序结束后数据不会持久化
- 不适合大规模知识库
- 不适合直接拿去做生产系统

所以更准确的定位是：

> 它是一个“帮助你看懂 RAG 原理”的最小实现，而不是生产版知识库架构。

## Retriever 才是面向问答链路的入口

建好向量库后，代码没有直接只做底层相似度查询，而是先把它转成检索器：

```js
const retriever = vectorStore.asRetriever({
  k: 3
})
```

这里的 `k: 3` 表示：每次取最相关的 3 条文档。

然后项目用这个问题发起检索：

```js
const question = "东东和光光是怎么成为朋友的"
const docs = await retriever.invoke(question)
```

这一步非常关键，因为它让 RAG 的工作流变得更清楚：

- 输入不是 SQL，也不是向量
- 输入就是自然语言问题
- 输出是最相关的文档片段列表

对初学者来说，`Retriever` 比“直接操作向量搜索 API”更容易理解，也更接近真实业务问答链路。

## 为什么这个 Demo 还专门看了分数

这个项目有个教学上很加分的地方：它不仅检索了文档，还补充调用了：

```js
const scoredResults = await vectorStore.similaritySearchWithScore(question, 3)
```

然后把命中的内容、分数和元数据打印出来。

这说明作者并不满足于“拿到答案”，而是想进一步理解：

- 为什么命中了这些片段
- 检索阶段的相关性大概如何
- 返回文档和原始相似度分数之间是什么关系

这在 RAG 学习里非常重要。因为很多时候你以为是“大模型回答不行”，实际问题往往更早出在检索阶段：

- 文档切分不合理
- embedding 模型不适配
- top-k 取值不合适
- 检索到的上下文本身就不准

需要特别说明的是：**这里的分数只能理解为检索相关性的线索，不能直接当成答案正确率。** 而且由于本文没有运行代码，也不能把具体分数效果表述成已验证结论。

## 真正的 RAG 增强发生在 Prompt 拼接这一步

检索到相关文档后，项目把它们拼成上下文：

```js
const context = docs
  .map((doc, i) => `[片段${i}]\n ${doc.pageContent}`)
  .join("\n\n------\n\n")
```

然后构造 Prompt：

```js
const prompt = `你是一个讲友情故事的老师。基于以下故事片段回答问题，用温暖生动的语言。如果故事中没有提到，就说"这个故事里还没有提到这个细节"。

故事片段:
${context}

问题：${question}

老师的回答:`;
```

很多人学 RAG 时只盯着“检索”，但这个 Prompt 其实同样重要，因为它决定了模型会不会老实用上下文回答。

这个 Prompt 至少做对了三件事：

1. **给角色**：让回答风格更统一
2. **给边界**：明确要求基于故事片段作答
3. **给兜底**：没有提到时，直接承认不知道

这正是 RAG 实用化时常见的基本约束方式。

## 最后一步：模型不是凭空回答，而是基于上下文生成

在上下文准备好后，项目才真正调用：

```js
const response = await model.invoke(prompt)
console.log(response.content)
```

所以整个数据流可以被浓缩成一句话：

> 文档先被向量化并进入向量库，问题再触发相似度检索，检索到的片段被拼进 Prompt，最后才由聊天模型生成回答。

这也是为什么 RAG 的回答通常比“裸问模型”更可控——因为它至少多了一层显式证据输入。

## 这个 Demo 最适合初学者学什么

如果你是第一次看 RAG，我认为这个项目最值得学的不是 API 名字，而是下面这几个认识：

### 1. 检索和生成是两个阶段

不是模型自己记住知识库，而是先查再答。这个认知一旦建立，后面很多设计就顺了。

### 2. 文档结构比你想象中重要

`pageContent` 决定召回内容，`metadata` 决定后续是否能做过滤、归类和溯源。哪怕在 demo 阶段，结构意识也应该先建立起来。

### 3. 向量库可以很简单，但流程必须完整

哪怕只是 `MemoryVectorStore`，只要你经历过“建库—检索—拼接—生成”完整流程，就能理解生产系统为什么要替换成更强的存储方案。

### 4. Prompt 不是装饰，而是回答边界

检索只是把资料拿回来，怎么用这些资料、缺信息时该不该胡编，最终还是要靠 Prompt 约束。

## 它离真实业务系统还差什么

如果把这个 demo 放到生产视角，它明显还缺几层关键能力：

- **知识来源外置**：现在文档直接写在代码里，不方便维护
- **文本切分策略**：真实长文通常要按 chunk 切分
- **持久化向量库**：例如 PostgreSQL + pgvector、Milvus、Qdrant 等
- **检索过滤与重排**：仅相似度不一定足够
- **引用与溯源展示**：回答最好能带出处
- **接口或页面封装**：现在更像实验脚本，而不是可交互应用

所以如果你准备继续往下学，可以按这个顺序升级：

1. 先把知识库换成外部文件加载
2. 再引入文本切分器
3. 然后替换为持久化向量数据库
4. 最后补上引用展示和应用层封装

## 我对这个项目的整体判断

这个 `rag-demo` 的最大价值，不是“功能多强”，而是“用最少代码把最关键的原理讲清楚了”。

对于刚接触 RAG 的开发者来说，它非常适合建立第一层正确认知：

- RAG 不是模型自动知道私有知识
- 检索质量会直接影响最终回答质量
- 向量库、检索器和 Prompt 是一个连续链路，不是彼此孤立的组件

如果把它当作学习样本，它是很合格的；如果把它当成可直接上线的知识库问答系统，它还远远不够。

## 写在最后

如果你现在正准备从“看懂 RAG”走到“自己实现一个可扩展版本”，那这个 demo 很适合作为第一块跳板：先把最小闭环彻底吃透，再去接文件加载、文本切分、外部向量库和前后端交互，学习曲线会顺得多。
