# Agent 负责想，Workflow 负责做：AI 应用为什么需要双层架构

如果让 AI 处理“查订单、校验退款资格、创建工单”这类任务，你会选择固定流程，还是让模型自己决定每一步？

答案通常不是二选一：**让 Agent 负责理解和决策，让 Workflow 负责可靠执行。**

## 先建立一个判断标准

| 如果任务…… | 更适合 |
|---|---|
| 步骤固定、规则明确、需要审计 | Workflow |
| 目标开放、步骤不确定、要结合上下文规划 | Agent |

核心差别不在于“是否使用大模型”，而在于**路径是否预先确定**。

## Workflow：确定性的 AI 流水线

Workflow 先把节点和路由画好，再按规则执行：

```text
简历 PDF
  → 文本解析
  → 提取技能/经历/学历
  → 匹配岗位要求
  → 输出结论
```

每个节点只做明确的事情，输入输出可定义，条件满足就流向下一步。

它适合：审批、数据清洗、结构化提取、报表生成等流程化任务。

优势是稳定、可控、容易追踪；限制则是遇到流程外的问题时不够灵活。

## Agent：目标驱动的动态执行者

Agent 接到的是目标，而不是固定步骤。它会：

```text
感知上下文和工具
  → 规划下一步
  → 调用工具
  → 根据结果调整计划
  → 完成目标
```

例如用户要求规划旅行，Agent 可能查机票、酒店、天气、签证，并根据预算重新权衡。每次任务的路径都可能不同。

这带来灵活性，也带来不确定性：模型可能绕路、调用不必要工具，甚至在关键动作上做出不合适的决策。

## 组合方式：大脑 + 骨架

一个更接近生产实践的设计是：

```text
用户问题
  → Agent：识别意图、规划、路由
  → Workflow：查询/校验/写入等标准操作
  → Agent：组织最终回复
```

以客服退款为例：

```text
Agent 判断：退款咨询
  → Workflow 查询订单
  → Workflow 校验退款条件
  → 必要时创建工单
  → Agent 向用户解释结果
```

这样既能处理自然语言的多样表达，又不会让模型直接自由操作关键业务。

## 三条工程边界

为了让 Agent 可用而非“不可控”，要至少考虑：

1. **工具白名单**：限制可调用能力。
2. **最大步数/预算**：防止循环和成本失控。
3. **高风险确认**：删除、退款、支付等操作进入人工确认或确定性校验。

## 一句面试回答

> Workflow 的路径预先定义，适合稳定、重复、强调可控和审计的任务；Agent 会基于大模型动态感知、规划并调用工具，更适合开放性问题。生产系统通常用 Agent 做意图识别和路由，用 Workflow 执行关键标准化操作，从而兼顾灵活性与可靠性。

## 结语

别把 Agent 当作“更高级的 Workflow”，也别把 Workflow 看成“没有智能的旧方案”。两者分别解决“如何思考”和“如何可靠落地”的问题。把它们组合起来，才是 AI 应用从 Demo 走向工程化的一条实用路径。
