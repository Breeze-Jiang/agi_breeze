## 核心知识

### 1. SDD 是什么

**材料事实：** SDD 是 `Spec-Driven Development`，即规范驱动开发。材料强调“文档即是代码”，把清晰、可执行、可验证的规范作为 AI 协作开发的重要输入。[E1]

**为什么需要：** 当代码生成成本变低时，真正稀缺的不是敲代码速度，而是明确的意图、边界和验收方式。规范可以减少 AI 根据模糊描述自行猜测。

**适用边界：** SDD 不是让文档替代代码，也不是保证 AI 代码一定正确；它是先完成设计和约束，再让 Agent 执行，并持续验证的开发流程。

### 2. Vibe Coding 的问题

材料把 Vibe Coding 描述为在 AI 交互窗口中持续下任务、快速生成代码的方式。短期看起来效率很高，但笔记指出，第一天的效率提升可能在后续带来返工。[E2]

主要问题包括：

- 给大模型的上下文不够；
- 会话历史丢失，缺少持久化上下文；
- AI 需要猜测框架、技术方案和业务边界；
- 生成结果看起来能运行，但后续会积累维护问题；
- 每次失败都会消耗等待时间和 Token。

材料中的典型模糊需求是“帮我做一个用户认证系统”。在没有技术栈、接口、权限边界和验收标准时，AI 可能直接生成大量代码，但代码量不等于方案正确。[E3]

### 3. 两次创造

材料借用“先设计蓝图再盖房子”的思路，把开发拆成两次创造：[E4]

```text
第一次创造：人在文档中设计系统
第二次创造：Agent 根据规范生成代码
```

第一次创造解决“系统应该是什么样”；第二次创造解决“如何把确定的方案落地”。如果跳过第一次创造，就容易把设计决策交给 AI 临场猜测。

### 4. 四类核心文档

| 文档 | 主要回答的问题 | 材料定位 |
|---|---|---|
| 需求文档 / PRD | 做什么、用户需要什么 | 产品需求 |
| `proposal.md` | 系统应该是什么样，满足什么需求 | 心智创造、方案表达 |
| `design.md` | 技术上怎么实现 | 技术设计 |
| `task.md` | 先做什么、后做什么、哪些可以并行 | 执行计划 |

三份规划文档完成后，代码才进入第二次创造。它们不是一次性写完就不变，而是随着理解和验证持续迭代。[E5]

### 5. Agent 与辅助工具的关系

材料列举了 Claude Code、Codex 等 Agent，以及 Cursor、Trae、Copilot 等辅助工具。这里可作合理推断：工具能力不同，但都需要高质量上下文；SDD 关注的是输入规范和执行流程，而不是某一个具体工具。

具体工具的版本、能力边界和配置未在材料中验证。

材料提到 Spec-kit 是规范驱动开发框架，帮助快速构建符合规范的代码。[E6]

## 重点语法与 API

本主题没有源码 API，重点是文档产物的职责：[材料中出现]

- `proposal.md`：表达目标系统、需求和整体方案。
- `design.md`：记录技术实现方案。
- `task.md`：拆解执行顺序、依赖和并行任务。
- PRD：描述产品需求。

[外部补充] 在实际团队中，规范通常还需要包含验收标准、异常边界、非功能要求和变更记录；本材料没有提供这些字段的具体模板。

## 注释重点解读

材料没有代码注释，但笔记中的解释性句子具有方法论注释作用：

- “先撰写文档，在编写代码”：强调设计先于实现。
- “不画蓝图就不盖房”：说明规范是降低返工的重要前置条件。
- “第一次创造 / 第二次创造”：帮助区分需求设计与代码实现，而不是把两者混为一次聊天生成。

需要注意，笔记中的“代码生产效率非常高，可以忽略不计”是观点性表达，不应理解为所有项目中代码成本真的可以忽略。

## 面试高频知识

### 什么是 SDD？[材料中出现]

> SDD 是规范驱动开发，先通过需求、方案、技术设计和任务拆分形成可执行规范，再让 AI Agent 根据规范生成代码，并在过程中持续迭代和验证。

### SDD 解决什么问题？[材料推导]

它主要解决 AI 编程中的上下文不足、需求歧义、会话不可持久化、生成结果难验证和后期返工问题。

### `proposal.md`、`design.md`、`task.md` 有什么区别？[材料中出现]

`proposal.md` 说明目标和需求表达；`design.md` 说明技术实现；`task.md` 说明执行顺序、依赖关系和并行拆分。

### SDD 和 Vibe Coding 的区别？[材料推导]

Vibe Coding 更偏即时对话和快速生成，容易把设计决策交给 AI 猜测；SDD 强调先沉淀规范，再让 AI 执行，重点从“多生成代码”转向“提供清晰、可执行、可验证的意图”。

### SDD 能保证 AI 代码正确吗？[材料推导]

不能。它只能改善上下文和决策过程，仍需要代码审查、测试和验收。当前材料没有提供运行验证结果。

## 复习卡片

> [!tip] 心智模型
> 先回答“做什么”，再回答“怎么做”，最后回答“先做什么”。

1. SDD 的全称是什么？—— Spec-Driven Development。
2. SDD 的核心顺序是什么？—— 先规范，后编码。
3. Vibe Coding 的主要风险是什么？—— 上下文不足导致 AI 猜测、幻觉和返工。
4. 两次创造分别是什么？—— 文档中的心智创造、代码中的物理创造。
5. PRD 解决什么问题？—— 明确产品需求。
6. `proposal.md` 解决什么问题？—— 描述系统目标和需求表达。
7. `design.md` 解决什么问题？—— 描述技术实现。
8. `task.md` 解决什么问题？—— 拆解执行顺序和并行关系。
9. 文档写完后是否不能修改？—— 不是，SDD 强调持续迭代。
10. SDD 是否等于某个工具？—— 不是，Spec-kit 是被材料提到的框架，SDD 是开发方法。

> [!warning] 易混淆
> “AI 能生成代码”不等于“AI 理解了需求”。代码生成前的上下文、边界和验收标准仍需由开发者明确。
