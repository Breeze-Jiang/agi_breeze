# Vibe Coding 不等于一句话生成项目：用规划和胶水编程降低 AI 幻觉

让 AI “写一个 React 待办清单”，看起来效率很高，但经常得到两类结果：代码能跑却需求不对，或者看似完整、一运行就报错。

问题通常不在于 AI 不会写 JSX，而在于：需求、边界、数据结构和依赖方案都没有被约束。

本文根据 [Vibe Coding 笔记](file:///C:/Users/38335/Desktop/workspace/jzh_ai/ai/vibe/demo-1/readme.md) 整理。当前 [list 项目](file:///C:/Users/38335/Desktop/workspace/jzh_ai/ai/vibe/demo-1/list/src/App.jsx) 仍是 React/Vite 默认计数页，待办清单和拖拽功能尚未实现，以下内容是协作方法与规划案例，不是已交付项目成果。

## 先转变一个定位：AI 是协作开发者

新手容易把 AI 当成“自然语言编程按钮”：输入一句需求，期待直接拿到可发布项目。

更可靠的做法是把它当成刚加入项目的同事：先让它了解技术栈、业务边界和约束，再分阶段协作。

```text
需求描述
  → 规划文档
  → 人工审核与修改
  → 小步编码
  → 运行、检查、反馈
```

## 第一阶段只做规划，不生成代码

以 React 待办清单为例，先给出明确指令：

```text
第一阶段只输出规划，不要输出代码。
技术栈：React 19 + Tailwind CSS + useState。
功能：新增待办、删除待办、切换完成状态。
不做：本地持久化、筛选、拖拽。
拆分输入框、待办条目、列表容器。
任务数据结构固定为 { id, text, completed }。
```

这段规划的价值不只是“让 AI 想清楚”，更重要是锁定约束。

### 功能边界要写清楚

没有写“不做本地持久化”，AI 可能自行引入 `localStorage`；没有写“不做筛选”，它可能多写一套筛选状态；没有确定数据结构，它可能混用 `title`、`content`、`text` 等字段。

先写边界，才能减少需求漂移。

### 数据结构要由人确认

```js
{ id, text, completed }
```

字段名看起来是小事，但它会贯穿组件 props、状态更新、接口数据和测试。越早固定，AI 后续生成的代码越一致。

## 第二阶段：胶水编程，而不是重复造轮子

遇到复杂能力，例如拖拽排序，不建议让 AI 从零实现坐标监听、碰撞判断和排序算法。

更好的指令是：

```text
为现有待办列表接入一个成熟且与当前 React 版本兼容的拖拽方案。
先说明选型依据和安装命令。
只输出组件适配、任务数据重排和状态更新的代码。
不要手写底层拖拽算法。
```

这就是“胶水编程”：

```text
成熟库 / 成熟组件
       ↓
少量适配与数据流转代码
       ↓
满足当前业务需求
```

胶水代码不负责重新发明零件，只负责将零件可靠连接起来。它可以显著减少复杂边界条件带来的错误，也更容易维护。

## 第三阶段：把有效经验写进规则

一次成功的提示词不应只留在聊天记录里。可以把稳定规则沉淀为项目说明：

- 固定技术栈与版本；
- 目录和命名规范；
- 新依赖必须先说明原因；
- 修改前先列出影响文件；
- 每次完成后执行哪些检查；
- 不确定时先提问，不要猜测字段和 API。

这相当于为 AI 准备“项目入职手册”。后续协作时，AI 带着相同约束工作，输出会更一致。

## 当前 Demo 的真实状态

```jsx

```

所以现阶段最合理的下一步不是直接添加一堆功能，而是先把待办清单规划写成可执行任务，再逐个实现组件和状态。

## 总结

Vibe Coding 的核心不是“少写代码”，而是“提高生成代码的可控性”：

1. 先规划，明确技术栈、边界、模块和数据结构。
2. 先审核规划，再开始编码。
3. 复杂通用能力优先选择成熟方案。
4. 用少量胶水代码完成集成与数据流转。
5. 将有效约束沉淀为项目规则，持续优化协作过程。

## 面试表达

> 在 AI 辅助开发中，我会先让模型输出技术选型、功能边界、模块划分和数据结构，确认后再分步骤实现。对于复杂通用能力，优先使用成熟库，自己重点关注适配、数据流和验证。这样可以避免 AI 擅自扩展需求、字段不一致和重复造轮子的问题。
