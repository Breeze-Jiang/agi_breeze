# 让 AI 先写规划，再写代码：我对 Vibe Coding 的一次拆解

“帮我写一个 React Todo List。”

这句提示词很自然，但它没有回答几个关键问题：要不要本地存储？要不要筛选？是否支持拖拽？任务字段叫什么？能否安装依赖？

这些空白会让 AI 自己补全。补得好是惊喜，补得不好就是需求漂移和幻觉代码。

下面用一个 React 待办清单案例，总结一套更稳的 Vibe Coding 协作方式。材料来自 [项目笔记](file:///C:/Users/38335/Desktop/workspace/jzh_ai/ai/vibe/demo-1/readme.md)。目前 Demo 代码仍是默认计数器，未完成待办功能，因此本文只讨论规划与方法，不宣称功能已上线或已验证。

## 先让 AI 进入“规划模式”

第一步不让它写代码，而是明确要求：

```text
第一阶段：只做规划，禁止输出代码。
技术栈：React 19、Tailwind CSS、useState。
功能：新增、删除、切换完成。
不做：持久化、筛选、拖拽。
模块：输入框、待办项、列表容器。
数据结构：{ id, text, completed }。
```

这相当于先写一个迷你 PRD 和技术设计。

好处有三个：

- **边界明确**：避免 AI 擅自加本地缓存、筛选和优先级。
- **结构明确**：组件先拆好，后续代码更易读。
- **字段明确**：不会一会儿用 `title`，一会儿又用 `text`。

## 审核规划比审核一大坨代码便宜

规划有问题时，改一行文字就够了；代码写完再发现“其实不要拖拽”，就需要删组件、删状态、删依赖，成本更高。

所以协作顺序应该是：

```text
规划 → 人工确认 → 实现一个小模块 → 检查 → 再继续
```

而不是：

```text
一句话需求 → AI 生成全部代码 → 最后一起排错
```

## 胶水编程：不要让 AI 从零写复杂底层逻辑

以拖拽排序为例，手写需要处理鼠标/触摸事件、坐标、占位、重排和大量边界条件。

更好的方式是先选成熟方案，再让 AI 做集成：

```text
成熟拖拽库
  + 现有 TodoItem 组件
  + tasks 状态更新
  = 可维护的拖拽排序功能
```

这里的“胶水”就是适配代码：传数据、接事件、更新状态。它不生产复杂零件，只负责把成熟零件连通。

需要注意：具体库不能只看“过去很流行”，还要确认是否仍维护、是否与当前 React 版本兼容。

## 把提示词升级成项目规则

每次都重新解释项目规范很浪费。更好的方式是在项目中沉淀规则：

```text
- 只能使用已确认的技术栈
- 添加依赖前先解释用途
- 修改前说明影响范围
- 不确定的数据字段先询问
- 完成后给出检查方式和未验证项
```

这样 AI 不再只是一次性聊天工具，而是带着上下文的协作助手。

## 我得到的结论

Vibe Coding 不应该理解成“用自然语言跳过工程化”。相反，它更需要工程化：

- 用规划限制随机性；
- 用成熟方案降低复杂度；
- 用小步修改控制风险；
- 用规则沉淀有效协作经验。

一句话总结：**AI 可以很快地产生代码，但人要先决定它该在什么边界内工作。**
